## Blocker

### QA-001: First-run setup can't create the admin, so the whole install is unusable
- **Area:** onboarding
- **URL:** https://openfront-pharmacy-production.up.railway.app/dashboard/init
- **Steps:**
  1. Open any URL on the fresh install. You are redirected to `/dashboard/init`.
  2. Enter Name `QA Admin`, Email `qa@openship.org` and a 24-character random password (letters, digits, symbol), then click **Create account**.
- **Expected:** As in E-commerce, the admin user and an `Admin` role with every permission are created, you are signed in, and you land on `/dashboard` (then onboarding).
- **Actual:**
  - A red "ERROR · Unable to create the initial user. Please try again." badge appears and you stay on `/dashboard/init`. The server action returns `{"message":"Unable to create the initial user. Please try again."}`.
  - `/dashboard` and `/` still return 307 to `/dashboard/init`, and `{ redirectToInit }` still returns `true`.
  - Retrying gives the same result. Nobody can ever use this install, the storefront included.
- **Real error** (from sending the server action's `createInitialUser` mutation to `/api/graphql`):
  ```
  KS_PRISMA_ERROR  path: ["createUser"]
  Invalid `prisma.user.create()` invocation:
    data: { name: "QA Admin", email: "qa@openship.org", password: "$2a$10$…",
            role: { connect: { id: undefined, ? name?: String, … } }, tokenVersion: 0, onboardingStatus: "not_started", … }
  Argument `connect` of type RoleWhereUniqueInput needs at least one of `id` or `name` arguments.
  ```
  The nested `role: { create: { name: 'Admin', …every permission } }` from `initFirstItem.itemData` doesn't produce an id. Keystone then sends `role.connect.id = undefined` and Prisma rejects it.
- **Notes for the fixer:**
  - `@keystone-6/auth` runs this as `context.sudo().db.User.createOne({ data: { ...fields, ...itemData } })`, so access control isn't the cause. Keystone's `NestedMutationState.create` returns `{ id: item.id }`, so `item.id` is coming back undefined somewhere in the nested Role create or in the User `resolveInput` hook.
  - Pattern across verticals:
    - **Rideshare** fails with the identical error. It builds the role with `Object.fromEntries(permissionNames.map(...))`, just like Pharmacy (`Object.fromEntries([['name','Admin'], ...permissionsList.map(...)])`).
    - **Salon** and **Medspa** set up fine on production. They build the role from a literal object. Salon also has the same "restrict public create fields" `resolveInput` hook as Pharmacy.
    - Start by comparing those, then reproduce `createInitialUser(data:{name,email,password})` on a fresh scratch database.
  - Short passwords stop earlier at password validation (min 12, `rejectCommon`). Only a valid password reaches the failing insert.
- **Likely files:**
  - `features/keystone/index.ts:148-163` (`initFirstItem.itemData.role.create`)
  - `features/keystone/models/User.ts:21-29` (`resolveInput`) and `features/keystone/security/user-create.ts` (`resolvePublicUserCreateData`)
  - `features/keystone/models/Role.ts`, `features/keystone/models/fields.ts` (`permissionsList`)
  - `features/dashboard/actions/auth.ts:96-103`, which hides every cause behind one message (see QA-012)
- **After the fix:** run setup on production with the password in the login file, set `loginReady: true`, and re-run this QA.

## Major

### QA-002: Anonymous GraphQL errors return Prisma debug output, including the bcrypt password hash and the full input
- **Area:** onboarding (security; applies to the whole API)
- **URL:** `POST /api/graphql`
- **Steps:**
  1. Without signing in, send any mutation that fails in Prisma. The QA-001 `createInitialUser` call is one, and it needs no session on a fresh install.
- **Expected:** A production API returns a masked error (`KS_PRISMA_ERROR` / "Prisma error") with no `extensions.debug`.
- **Actual:**
  - The response includes `extensions.debug.message`, the full 2,193-character Prisma invocation.
  - That covers the user's email, the **bcrypt hash of the submitted password**, every field written, and the Role filter schema with all 19 permission names.
  - GraphiQL (the Apollo Sandbox page) and schema introspection are also open to anonymous callers.
- **Note:** `pages/api/graphql.ts` and the Keystone config match E-commerce, so this probably affects every vertical. Keystone adds `debug` only when `graphql.debug` is true, which defaults to `NODE_ENV !== 'production'`. Either production runs with a non-production `NODE_ENV` in the Keystone context, or debug needs to be forced off.
- **Likely files:** `features/keystone/index.ts:181-203` (no `graphql.debug: false`), `pages/api/graphql.ts` (no `maskedErrors`, GraphiQL always on)

### QA-003: Card payment (Stripe) can't work on the storefront, so online orders are "Pay at pickup" only *(code-read)*
- **Area:** storefront
- **URL:** `/checkout`
- **Steps:**
  1. After setup, install the Stripe payment provider (it's seeded with `isInstalled: false`) and add an item to the cart.
  2. At checkout, choose **Stripe** and click **Place order**.
- **Expected:** As in E-commerce (`openfront/features/storefront/modules/checkout/components/payment-wrapper/stripe-wrapper.tsx`), a card form (Stripe Elements) collects the card, confirms the PaymentIntent in test mode, and the order is placed.
- **Actual:**
  - The checkout has no card form at all, only a provider pill.
  - `initiatePharmacyPaymentSession` creates a PaymentIntent. Its status is `requires_payment_method`, which `paymentOperations.ts:34` maps to `requires_action`.
  - `placeOrder` then always returns "Card payment is not available online yet. Choose another payment option."
  - `@stripe/stripe-js` and `@stripe/react-stripe-js` aren't dependencies.
- **Business impact:** Delivery orders can't be prepaid (see QA-009), and a pharmacy can't take online payment on day one.
- **Likely files:**
  - `features/storefront/lib/data/checkout.ts:41`
  - `features/storefront/components/CheckoutForm.tsx:72-76`
  - `features/integrations/payment/stripe.ts` (returns `clientSecret`, which the storefront never uses)

### QA-006: Customer password reset doesn't work: no mail transport in production, and the link goes to the admin reset page *(code-read)*
- **Area:** storefront
- **URL:** `/account/reset`
- **Steps:**
  1. Click **Forgot password?** on `/account`, enter a customer email and submit.
- **Expected:** The customer receives an email with an absolute link to the storefront reset page `/account/reset?token=…`, where the email field is prefilled.
- **Actual:**
  - Production has only `DATABASE_URL`, `SESSION_SECRET` and `S3_*`, so there's no `SMTP_HOST`. For a real account, `transport.sendMail` throws and the customer sees a generic error. The UI doesn't say email isn't configured.
  - Even with SMTP set, the email link is `${SMTP_STORE_LINK}/dashboard/reset?token=…`. That sends customers to the **admin** reset screen, and the link is relative when `SMTP_STORE_LINK` is unset.
  - The storefront reset form needs both the email and the token, but the link carries only the token.
- **Likely files:**
  - `features/keystone/lib/mail.ts:6-14` and `:61-71`
  - `features/keystone/index.ts:164-168` (`passwordResetLink.sendToken`)
  - `features/storefront/screens/ResetPasswordPage.tsx:22-25`

### QA-011: Order dates are formatted in the server's time zone, not the pharmacy's *(code-read)*
